# Account state, catalogue and session synchronization

The server advertises `account_events_v2`, `shuffle_presets`, `last_track`,
`session_management`, `catalogue_events`, and `playback_resume` as capability value `"1"`.
All account routes are under `/api` and require the authenticated account.

## Account revision vectors

`GET /account/state` returns `user_id`, `username`, lowercase `role`, and
`revisions: {collections, presets, statistics, playback}`. The independent counters belong
to that account. Statistics revisions live in the statistics database and are
committed in the same transaction as accepted counter/legacy contributions,
consent changes, resets, and reporting genre changes. Reset generations and
per-device sequence/consent fences are independent of notification revisions.
Simultaneous listening from separate devices adds both devices' contributions.

Open `GET /account/events` before fetching snapshots. The `account` SSE event
contains `{kind, revisions}`. `ready` confirms the subscription is installed;
`revision` invalidates changed domains; `account_changed` requests account
metadata refresh. Fetch each domain's authoritative snapshot and compare its
revision with buffered events. The stream checks durable revisions at least
every 15 seconds, repairing missed in-memory publication. Reconnect, foreground
recovery, database restore, and identity/account changes require fresh snapshots,
including when revisions are lower than previously observed. Events are hints,
not replayable patches. Foreign account changes never emit private vectors.
The original collection snapshot/event endpoints remain available.

## Saved custom shuffle presets

`GET /account/shuffle-presets` returns `{revision, items}`. Each item is
`{id, name, artist_ids, genres, revision}`. IDs are generated by the server.
Create with `POST /account/shuffle-presets` and a name/filter object; update with
`POST /account/shuffle-presets/:id` plus `expected_revision`; delete using
`DELETE /account/shuffle-presets/:id?expected_revision=N`. Create/update returns
the complete item; delete returns 204. Missing update preconditions return 428;
stale edits/deletions return 409. Refresh and let the user review conflicts;
do not automatically replace a newer preset. Names are trimmed and limited to
80 characters. Filters are trimmed/deduplicated; genres are case-normalized.
Missing artists/genres can remain in a saved rule for future catalogue recovery.

Preset and account revision writes are atomic in additive side tables; existing
playlist and authentication record encodings are unchanged. Preset mutations do
not modify a playing queue or change an active shuffle session.

## Track seed for a new independent playback session

Clients supporting `playback_resume` use the richer private checkpoint and
durable shuffle deck contract in [playback-resume.md](playback-resume.md).
The seed endpoint remains available for older clients. An accepted legacy start
atomically changes the richer suggestion to that track in standalone context.

`GET /account/last-track` returns `{track_id: string|null, revision}`. Removed or
unavailable catalogue tracks are returned as null. `POST /account/last-track`
accepts `{track_id, session_id, sequence, request_id}` after an actual successful
track start and returns that same snapshot shape. Tracks must exist in the
current catalogue. Use a fresh runtime session nonce and monotonically increasing
positive sequence; retain the request ID when retrying that start. Repeated or
older starts from the same session cannot overwrite later accepted starts.
Concurrent devices are ordered by successful server commits, never client clocks.
Do not upload offline history/backlogs into this live seed endpoint.

A new client can prepare this track at position zero, paused, after its own
local restoration decision. The seed carries no seek position, queue, play/pause,
repeat, shuffle, volume, or remote control commands. Starting, seeking or stopping
one client never changes another client's existing playback session.

## Account access and session controls

`POST /account/sessions/revoke-others` returns `{revoked}` and preserves the exact
initiating token. `POST /account/sessions/revoke-all` returns the count and also
revokes that token; clients then clear the signed-in account locally. Both actions
revoke only app sessions and preserve admin console sessions for the account.
The token is revalidated inside the revocation write transaction. Other accounts'
sessions remain valid. Console administrators have a per-user **Sign out all app
sessions** action with confirmation at `/users/:user_id/sessions/revoke-all`, with
the same scope and Superadmin protection as existing account mutations. An
administrator can sign out their own apps while remaining signed into the console.

Console session purpose is persisted in an additive table without changing the
existing token encoding. Console logins created before this distinction have no
purpose metadata; sign into the console again once after upgrading to protect
that login from app-session revocation. Password changes, account edits/deletion
and server security resets retain their existing broader revocation behavior.

Authentication changes wake long-lived account/collection/catalogue responses
immediately. Streams recheck the database and close after logout, password or
role changes that revoke tokens, account deletion, or disabled/expired access.
Heartbeat checks are also retained, and QUIC continues its existing one-second
session revalidation. Outgoing pushes never count as incoming client presence.

## Structural catalogue changes

`GET /library/metadata-events` retains its `metadata` event format and adds
`kind: "catalogue"`, with `id` containing the opaque `browse_revision`. Successful
initial load, scan/reindex/root replacement and metadata restore publish a
catalogue marker after committed state becomes visible. An initial and periodic
15-second marker repairs missed notifications and detects a changed server
catalogue generation. Existing artist/album metadata notifications remain intact.
Clients compare the opaque ID and invalidate retained browse windows/cursors
without restarting playback or removing downloaded files.

## Verification without running services

`cargo check -p server --tests --offline` verifies all handlers. The
`account_collection_sync_test` foreground test executable exercises production
stores, authentication, in-process Axum requests and SSE bodies without opening
sockets or decoding audio. It covers account isolation, preset conflicts, seed
ordering, independent revision recovery, immediate revocation, accepted statistics
notifications and existing multi-device sum/reset/consent invariants. Console
checks use `node --test web/tests/users-update.test.mjs web/tests/console.test.mjs`
with DOM doubles and no browser or HTTP server. End-to-end running-app checks are
left to the user.
